# Durable Controller Plugin Development

Use for plugins that translate immutable plans into durable task graphs, worker handoffs, review gates, or external integration lifecycles.

For plugins that own a local Chromium process, expose loopback CDP, synchronize an isolated browser profile, or provide stable logical tabs, follow [references/browser-provider-lifecycle.md](references/browser-provider-lifecycle.md). For exact-target JavaScript execution and honest cross-tab concurrency, also follow [references/target-scoped-cdp-evaluation.md](references/target-scoped-cdp-evaluation.md); `Target.activateTarget` is not a target-isolation primitive.

For browser-takeover consent, establish the requested authorization surface before testing. If the user asks for an Edge/Chrome-native debugging or takeover permission, never substitute a chat confirmation, a synthetic localhost consent page, or an agent-clicked approval. Preserve the user's decision boundary: the human must operate the native browser permission or revocation UI. Follow [references/native-browser-takeover-consent.md](references/native-browser-takeover-consent.md) for Chromium's extension-permission, active-debugging, cancellation, and default-profile constraints.

## Non-negotiable workflow

1. **Constrain the write scope.** Confirm the plugin repository and never edit host/core code merely because the plugin imports it. Core may be inspected for public API signatures.
2. **Orient before changing code.** Read the manifest/entrypoint, state schema, controller lifecycle, and all plugin tests. Record the existing test command and clean git state.
3. **Use vertical TDD slices.** For each lifecycle boundary, add one behavioral test, run it red for the missing behavior, add the smallest implementation, then run that test green. Do not batch all tests before implementation.
4. **Inject external effects.** Git-hosting/PR/network behavior must sit behind a tiny injected protocol or client. Tests use a fake client and assert its payload and idempotency; production code must not secretly call a remote provider.
5. **Keep observer and controller roles separate.** Hooks record immutable observations only. A state transition requires an explicit authorization artifact that references the observation and has a replay-resistant identity.
6. **Treat durable state as an upgrade surface.** Use additive schema migrations, explicit columns in inserts, unique keys for idempotency/replay protection, and persisted audit events for state-machine transitions.
7. **Checkpoint finish work early.** Before the last large test run, run syntax checks and `git diff --check`, restore/remove generated bytecode or cache files, stage intended source/tests only, run the full suite, and commit. Do not leave cleanup/commit until after exploratory calls consume the tool budget.

## Lifecycle design checklist

### Dynamic child graphs
- Freeze one validated child graph per parent route; reject graph replacement.
- Validate child IDs, bounded attempts, source provenance, dependency references, duplicate edges, self-dependencies, and cycles.
- Dispatch only dependency-ready children.
- Give every child its own Dev → independent QA → judge/closure stages and acceptance evidence.
- A parent may enter `awaiting_children`, but must not become accepted until every child is independently accepted. A failed/exhausted child blocks parent closure.

### Run-owned branches and PRs
- Generate feature and integration branches from the durable run ID, not just a plan ID, so completed runs cannot collide with new ones.
- Persist base repository, base branch, feature branch, integration branch, and PR lifecycle state.
- Use a run-owned feature worktree for Dev work only; do not send a branch name with scratch QA tasks.
- Keep PR opening idempotent and, unless the user requests otherwise, require completed execution before opening it.

### Observer ledger and authorized advance
- Persist an append-only receipt containing task identity, event kind, normalized payload digest, predecessor digest, and entry digest.
- Observer receipt generation must not mutate route/task status.
- Authorized advance validates the completed receipt, task identity, actor, and a unique authorization ID before calling internal completion logic.
- Reject reused authorization IDs and duplicate/replayed proposal IDs with explicit errors.

### Ops governance
- Snapshot tracked governance files before creating run worktrees and persist snapshot ID plus digest.
- Create read-only Ops observer tasks linked to the snapshot.
- Accept only versioned maintenance proposals from registered Ops tasks; record them as proposals, not feature-branch mutations.

## Creator-facing notifications

When a controller creates a durable Kanban root, capture the originating Gateway routing descriptor at creation time through `gateway.session_context.get_session_env(...)`, with environment fallback only when no ContextVar value exists. Persist platform, chat ID, chat type, thread ID, user ID, session key, and notifier profile using `kanban_db.add_notify_sub`; do not infer a group/DM destination or hard-code a platform. A TUI-only session may use its session key as the local target; a CLI/cron caller without a durable target must remain unsubscribed rather than pretending to have chat delivery.

Treat controller notifications as a durable projection, not workflow truth. Write the controller event and an idempotent outbox record in controller state, then publish to the root Kanban `task_events` only after the controller transaction commits. Keep a persisted dedupe key in the published payload and mark the outbox row published only after verifying the root event exists, so restart/replay cannot duplicate creator messages. Notification delivery failures must never accept, unblock, or otherwise mutate execution state.

Reuse native Kanban notifier event kinds when available (`swarm_created`, `swarm_progress`, `swarm_blocked`, `swarm_completed`) so Gateway/TUI delivery remains centralized. A terminal `swarm_completed` payload must include a non-empty `synthesis_summary` grounded in the final verified handoff; generic completion text is insufficient.

For SQLite tests on Windows, close `kanban_db.connect(...)` explicitly (or use its closing helper). A bare connection context manager commits but does not necessarily release the DB handle before temporary-directory cleanup.

### Local plugin replacement pitfall

When deploying a replacement plugin, stage the new tree outside the active plugin directory, stop the Gateway, move the old tree to a backup root **outside** `$HERMES_HOME/plugins/`, then place the verified staged tree at the canonical plugin path and restart once. Do not keep a renamed backup (for example `<plugin>.backup-<timestamp>`) under `plugins/`: Hermes recursively discovers plugin manifests there, and a later-scanned duplicate with the same manifest name can override the active copy in `hermes plugins list` and at Gateway load time. Verify the canonical installed manifest hash/version, run `hermes plugins list --plain --no-bundled`, and only then perform a controlled installed-code smoke run.

## Verification and delivery checklist

Run in the plugin repository:

```bash
python -m py_compile controller.py task_refiner.py __init__.py
python -m unittest discover -s tests -v
git diff --check
git status --short
```

Before committing:
- Remove generated `__pycache__` / `.pyc` artifacts from the diff.
- Confirm tests include new behavior plus regression coverage.
- Ensure the final test run occurs **after** every last implementation or test adjustment.
- Commit only after all checks are green, then report the actual commit SHA and any unverified limitation.
