## Architecture: Two-phase decoupled pipeline

```
Phase 1 (register):  NX取号 → 纯协议注册(手机号+密码) → 入成品池标「待codex」
Phase 2 (finalize):  认领「待codex」号 → 同IP登录 → 绑pool_emails邮箱 →
                      拿AT/RT/ID token → 拿 chatgpt.com /api/auth/session → 标「正常」
```

Two phases run as **independent parallel loops** (`phone-reg-worker.js`: `registerLoop` + `finalizeLoop`). Failure in phase 2 doesn't waste the paid phone number — it returns to the pool.

## Sentinel anti-bot system

OpenAI uses Sentinel (`sentinel.openai.com`) on strong endpoints. Strong endpoints require `openai-sentinel-token` header; the strongest also require `openai-sentinel-so-token`.

### Strong endpoints (by flow name)
- `username_password_create` — POST `/api/accounts/user/register`
- `phone_otp_validate` — POST `/api/accounts/phone-otp/validate`
- `oauth_create_account` — POST `/api/accounts/create_account` (needs so-token via SentinelVM executing `snapshot_dx`)
- `password_verify` — POST `/api/accounts/password/verify`
- `checkout_session_approval` — POST `/backend-api/payments/checkout/confirm` (Plus activation)

### Sentinel token structure
Generated by `sentinel_v2.py`. Token is JSON with fields: `p` (PoW), `t` (turnstile proof), `c`, `flow`, `id`. The `SentinelVM` class executes `turnstile.dx` / `snapshot_dx` bytecode (a custom JS VM in Python).

### Current state of sentinel_v2.py
- Token JSON structure matches browser ✅
- PoW/turnstile proof values are **rejected by server** ❌ — the Python SentinelVM's execution results don't precisely match browser JS VM output
- This means pure-protocol approaches FAIL on Sentinel-protected endpoints that do server-side proof validation

## Plus activation: 5-step chain

```
1) POST /backend-api/payments/checkout → oaics_ + publishable_key (PH/PHP promo pricing)
2) POST /backend-api/payments/checkout/taxes → tax preview (non-blocking)
3) POST api.stripe.com/v1/confirmation_tokens → ctoken (card + US billing address)
4) POST /backend-api/payments/checkout/confirm → payment_intent client_secret  ← BLOCKED BY SENTINEL
5) POST api.stripe.com/v1/payment_intents/{pi}/confirm → succeeded/processing
```

**Step 4 is the blocker.** It's a Sentinel-protected strong endpoint (`checkout_session_approval` flow). Pure API calls return `blocked` because the confirm request lacks a valid `openai-sentinel-token`.

Steps 1-3 and 5 are pure Stripe/OpenAI API calls with no Sentinel protection and work reliably via `curl_cffi`.

## Hybrid bypass pattern: protocol + real browser (IMPLEMENTED)

When a single endpoint is Sentinel-protected but the rest of the pipeline works via pure API, use the **hybrid pattern**. This is now implemented in `plus_activate.py` (committed 2026-07-06).

### How it works
1. Keep all non-protected steps as pure API (fast, no browser overhead)
2. Switch ONLY the Sentinel-protected step to real Playwright browser
3. Browser loads the real page → Sentinel SDK executes natively in JS → generates 100% valid token
4. Intercept the browser's network response to get the result, feed back to the protocol pipeline

### For Plus activation specifically
- Steps 1-3: pure API via `curl_cffi` (unchanged)
- Step 4 (`checkout/confirm`): Playwright opens `checkout_url`, fills Stripe Elements, clicks subscribe, browser JS sends confirm with valid Sentinel token
- Step 5: pure API via `curl_cffi` (unchanged)

### Env vars controlling browser confirm
| Env var | Default | Purpose |
|---|---|---|
| `PLUS_USE_BROWSER_CONFIRM` | `1` | 1=browser confirm (default), 0=pure API fallback |
| `PLUS_BROWSER_HEADFUL` | `0` | 1=headed mode for debugging, 0=headless |
| `PLUS_BROWSER_TIMEOUT` | `120` | Browser confirm timeout in seconds |

Config keys (app_config): `phonereg_plus_browser_confirm`, `phonereg_plus_browser_headful`, `phonereg_plus_browser_timeout`.

### New functions in plus_activate.py
- `_pw_proxy_from_url(proxy_url)` — converts proxy URL to Playwright proxy dict
- `_fill_stripe_card(page, card, address)` — fills Stripe Elements iframe (merged + split modes)
- `_click_subscribe(page)` — finds and clicks subscribe button (6 selectors + fallback scan)
- `_confirm_via_browser(checkout_url, session, card, address, proxy_url, headless, timeout_s, promo, pk, st, sh)` — main browser confirm function, returns tri-state

### Design rules for the hybrid pattern
- **Use `page.on("response")` to intercept the protected endpoint's HTTP response** — don't rely on DOM changes (fragile)
- **Return three states** from the browser step: `True` (success), `False` (failure), `None` (got intent, need downstream step)
- **Fill Stripe Elements via `type(delay=50)` not `fill()`** — Stripe's JS requires keyboard events
- **Browser proxy must reach chatgpt.com** — residential proxies can't; use the 711 chain proxy
- **Don't touch sentinel_v2.py** — the browser generates valid tokens natively
- **Keep the pure API path as fallback** — `PLUS_USE_BROWSER_CONFIRM=0` reverts to original behavior

## Chain proxy for Cloudflare bypass

`chatgpt.com` is behind Cloudflare which does TLS JA3 fingerprinting. `httpx`/raw Python SSL gets 403. Solution:

```
curl_cffi (chrome JA3) → local ChainProxy → 7897(clash) → 711 US residential → chatgpt.com
```

The CONNECT tunnel only forwards bytes (TLS end-to-end), preserving curl_cffi's browser JA3. Config keys: `phonereg_session_chain_hop1` (e.g. `http://127.0.0.1:7897`) + `phonereg_session_chain_exit` (711 `host:port:user:pass`).

Residential proxies (rola) **block chatgpt.com domain entirely** (connection reset 56). They work for `auth.openai.com` but not `chatgpt.com`.

## Proxy routing for Plus activation

- **checkout (step 1)**: JP proxy (`phonereg_plus_proxy`) — gets 0元 eligibility
- **confirm (step 4)**: 711 US chain proxy — must reach chatgpt.com; browser uses same proxy via `_pw_proxy_from_url()`
- **blocked retry**: rotate the 711 exit session ID via `_rotatePayExit()`, retry up to N times

### Admin password reset
When the admin password is unknown (changed via UI, or `.env` mismatch), reset it directly in the DB:

```bash
cd <USER_HOME>\Documents\aduib-app\gpt_plus
node -e "
require('./env-loader')();
const store = require('./mysql-store');
const crypto = require('crypto');
async function main() {
  const pwd = 'NEW_PASSWORD';
  const salt = crypto.randomBytes(16).toString('hex');
  const hash = crypto.scryptSync(pwd, salt, 64).toString('hex');
  const fullHash = 'scrypt\$' + salt + '\$' + hash;
  await store.runExecute('UPDATE app_config SET config_value = ? WHERE config_key = ?', [fullHash, 'admin_password_hash']);
  await store.runExecute('UPDATE app_config SET config_value = ? WHERE config_key = ?', ['1', 'admin_password_version']);
  console.log('✅ Reset to: ' + pwd);
}
main().then(() => process.exit(0)).catch(e => { console.error(e); process.exit(1); });
"
```

Key details:
- `app_config` table columns are **`config_key`** and **`config_value`** (NOT `key`/`value` — this is a common mistake)
- `mysql-store.js` does NOT export `getPool()` — use `store.runExecute()` / `store.runQuery()` instead
- `admin_password_version` must be reset to `1` alongside the hash
- The hash format is `scrypt$<salt_hex>$<hash_hex>` (dollar-separated, 3 parts)
- No server restart needed — the next login attempt reads from DB

## Email pool management

The finalize phase requires Outlook emails with valid OAuth2 `refresh_token` + `client_id` (Graph API Mail.Read scope) to receive OpenAI OTP codes.

### Key facts
- **Buy from hotmail007.com** — config key `hotmail007_client_key` in `app_config`. API: `GET /api/mail/getMail?clientKey=xxx&mailType=outlook Trusted&quantity=N`
- **Always buy `outlook Trusted`** — regular outlook/hotmail frequently have `AADSTS90023` (no permissions) or `AADSTS70000` (banned). Trusted costs ~0.02 each, has valid Graph tokens.
- **Import formats**: `----` separator (recommended: `email----password----client_id----refresh_token`), colon separator, or tab/space (no OAuth2)
- **IMAP fallback is dead** — Microsoft disabled basic IMAP; only Graph API works for OTP retrieval
- **Health check before use**: batch-validate all pool emails' Graph tokens (POST to `login.microsoftonline.com/common/oauth2/v2.0/token` with scope `https://graph.microsoft.com/.default`). Bad emails waste finalize cycles.

See `references/email-pool-management.md` for API calls, health check script, table schema, and failure modes.

## Known pitfalls

1. `create_account` missing_email → must use chatgpt web client (not platform) for phase 1
2. `registration_disallowed` → missing so-token on create_account
3. `409 invalid_state` → after binding email, don't call password/verify again; break after email-otp/validate
4. `wrong_email_otp_code` → must use email_snapshot baseline dedup (exclude old OTP emails)
5. Subprocess hangs 30min → SMS polling in non-daemon thread; use `os._exit()` after marker flush
6. `invalid_phone_number` → NX US numbers often VoIP; worker auto-retries with new number
7. session `/api/auth/csrf` no cookie → must `GET /auth/login` first for CF clearance
8. `session/select` 403 → Cloudflare challenge, retry several times
9. `httpx`/raw SSL to chatgpt.com 403 → JA3 challenge, must use `curl_cffi(impersonate=chrome)`
10. 7897 exits HKG → 403 region not supported; chain exit must land in US
11. rola reset chatgpt.com → residential proxy blocks the domain; only chain proxy works
12. **407 Proxy Authentication Required** during registration → `phonereg_proxy` is empty and fallback `proxy` points to a remote residential gateway (e.g. `gw.galdor.cc:6100`) that can't be reached directly from China. Fix: set `phonereg_proxy` to the local clash inbound (`http://127.0.0.1:7897`), NOT the remote gateway. The Python httpx client in register/finalize connects through `PROXY` env directly — it does NOT go through Node's ChainProxy. Only the session-fetch and Plus-activation steps use ChainProxy (which chains hop1→exit).
13. **`AADSTS90023: No applicable permissions`** during finalize email OTP → the Outlook pool email's `refresh_token` lacks Mail.Read scope for Graph API. IMAP fallback also fails (`User is authenticated but not connected`) because Microsoft disabled basic IMAP. This is a **data quality issue in the pool email, not a code bug** — the worker will auto-retry with a different email, but if many pool emails have bad tokens, every finalize will stall. Fix: replace the bad email's refresh_token or mark it inactive. Buy `outlook Trusted` from hotmail007 to get emails with valid Graph permissions.
14. **`local_proxy` DB vs `.env` mismatch** → `app_config.local_proxy` in the DB can hold a stale value (e.g. `http://127.0.0.1:10808`) even after `.env` is updated to `7897`. The DB value is what some runtime paths read. When changing the local proxy, update **both** `.env` and the DB `app_config` entry.
15. **hotmail007 stock varies by mailType** — `outlook` and `hotmail` often show 0 stock; use `outlook Trusted` (25k+ stock) or `hotmail Trusted` (17k+ stock). Check stock first via `GET /api/mail/getStock?mailType=outlook%20Trusted`.
16. **hotmail007 `Purchase failed, please try again`** — transient error when stock for a specific type is depleted or the API is flaky. Retry or switch to a Trusted variant.
17. **`reservePoolEmail` picks lowest `id` first** — bad emails with lower IDs keep getting selected before good ones. After identifying dead emails via health check, immediately `UPDATE pool_emails SET is_active=0` for all bad IDs — otherwise finalize keeps retrying the same dead email in a loop (each retry wastes ~60s on IMAP timeout before failing).
18. **`IN (?)` doesn't expand arrays in mysql2 `runExecute`** — `runExecute('... WHERE id IN (?)', [badIds])` silently returns 0 affected rows. Loop and execute per-ID instead: `for (const id of badIds) await store.runExecute('UPDATE ... WHERE id = ?', [id])`.
19. **Product status "正常" but no token** — if finalize fails after email binding but the status was prematurely set to "正常" (without token/session), the finalize loop won't re-claim it (it only claims "待codex"). Manual fix: `UPDATE product_assets SET status='待codex' WHERE registration_phone='+xxx'` to re-trigger finalize on next loop tick.
20. **Worker does NOT auto-start on server boot** — `startPhoneRegWorker()` is only called when the user clicks "批量注册" or "一键" in the admin UI, or when `POST /api/admin/phone-reg/start-batch` is hit. If the server restarts, pending "待codex" accounts sit idle until the worker is manually triggered again.
21. **Stripe API `CONNECT tunnel failed` (curl 56)** — `api.stripe.com` has no Cloudflare JA3 challenge, so the 711 chain proxy is unnecessary AND harmful (CONNECT fails). The `st` (Stripe) curl_cffi session in `plus_activate.py` must use `LOCAL_PROXY` (clash direct), NOT the chain proxy. Fix: `st = _mk({"http": LOCAL_PROXY, "https": LOCAL_PROXY})`, NOT `st = _mk(proxies)`. The chain proxy is only needed for `chatgpt.com` endpoints (checkout, confirm).
22. **`name 'proxy' is not defined` in `_run()`** — the function signature is `_run(..., proxies, ...)` where `proxies` is a dict `{"http":url,"https":url}`. There is no `proxy` (singular string) variable. Browser confirm code that references `proxy` directly will NameError. Fix: read the proxy URL from env (`SESSION_PROXY` → `PROXY` → `LOCAL_PROXY` fallback chain), not from a non-existent variable.
